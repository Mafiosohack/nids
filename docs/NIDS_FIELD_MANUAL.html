01What it is, in one paragraph

A network intrusion detection sensor that captures live traffic, runs 38 catalogued detection rules against it, groups the resulting alerts into kill-chain incidents by attacker, and serves the whole thing through an authenticated REST API and a real-time dashboard. Three companion sensors — a host auth-log reader, a cloud VPC-flow-log reader, and a flow-based machine-learning classifier — post into the same alert pipeline, so evidence from four different telemetry sources lands on one timeline.

The thing that distinguishes it from a student NIDS project is not the rule count. It is that every claim it makes is falsifiable. Each alert names a stable rule ID and carries the measured feature that triggered it, so the verdict can be checked rather than trusted. Each rule declares which detail keys it must produce, and an automated harness fails any alert that omits them. And the documentation states, up front, the categories of attack this sensor structurally cannot see.

The framing that matters

Most of the interesting engineering here is in the discriminators — the specific measurement that separates two things that look alike on the wire. A SYN scan and a connect scan both spray SYNs; the discriminator is the client's third packet. A brute-force tool and a patient human both retry logins; the discriminator is measured attempts per second. A reverse shell and a legitimate SSH session are the same kind of session; the discriminator is an out-of-band confirmation from the host sensor. Being able to name the discriminator for each rule is the whole skill.

02Architecture: what it is made of

The central structural decision: detection logic is a pure library, and the server is a wiring layer. Everything in detection/ imports no scapy, no FastAPI, no sockets. Every detector takes an injected clock instead of calling time.time(). That makes the whole detection surface testable in milliseconds with no network, no privileges and no sleeping.

The payoff is that detection/pipeline.py composes the detectors once, and three callers drive that same object: the live sensor, the 163 unit tests, and the efficacy harness. There is no parallel test reimplementation that can drift from production.

Process model

Four processes, loosely coupled by one HTTP endpoint:

  main.py            capture thread + FastAPI (uvicorn) + SQLite
       ▲                POST /alert  ·  X-Sensor-Key pre-shared key
       │
       ├── live_ids_v2.py       flow features → ML model → alert
       ├── host_log_sensor.py   /var/log/auth.log → alert
       └── cloud_log_sensor.py  VPC flow logs → alert

The sensors are deliberately separate processes rather than threads. Each needs different privileges (raw capture vs log file read), each can be deployed on a different host, and a crash in one does not take the dashboard down. They authenticate with a pre-shared key on a header that is not accepted for any read endpoint — a compromised sensor key lets you inject false alerts, never read real ones.

Single alert path

Every alert in the system, from every source, takes exactly one route:

Finding ─→ pipeline.publish() ─→ dedup/retention ─→ correlation ─→ _on_published_alert()
                                                              │
                                          ┌───────────────────┼────────────────────┐
                                          ▼                   ▼                    ▼
                                    SQLite insert      console log         kill-chain state
Why one path

The previous design had the correlation engine calling back into alert generation, which re-entered correlation. That re-entrancy meant an incident could ingest the very alert announcing itself, inflating its own event count and listing itself among its member rules. Funnelling everything through one publish function, with the correlator explicitly forbidden from ingesting correlation-tier output, removes the whole class of bug.

03The packet path, step by step

This is the sequence to be able to recite. A packet arrives at process_packet() and passes through these stages in this order.

Step 0 — Layer 2

ARP has no IP layer, so it is handled before the IP guard. MITM_ARP_SPOOF and ASSET_ROGUE_HOST both fire here.

Step 1 — Fragment reassembly

If the packet is a fragment it goes into the reassembler and the function returns early until the datagram is whole. See §5 for why this must happen before anything else.

Step 2 — Protocol-agnostic volume checks

Run on every IP packet regardless of transport: DDoS packet rate, cloud metadata (IMDS) access, bulk exfiltration bytes, and internal data staging.

Step 3 — TCP into the pipeline

PIPELINE.on_tcp_packet() receives source, destination, both ports, flags, up to 4096 bytes of payload, the true payload length, the sequence number, the fragment count, and an outbound flag. Inside, in strict order:

  1. Flag signature — a single-packet test on the TCP flags byte, producing TCP_NULL_SCAN, TCP_FIN_SCAN, TCP_XMAS_SCAN or TCP_SYNFIN_SCAN.
  2. On a bare SYN — port-scan accumulation, brute-force accumulation, the vsftpd second-stage check, outbound-anomaly check, beacon check-in, and flow open for both the shell and TLS detectors.
  3. On SYN-ACK — the handshake table advances (needed for the -sS vs -sT discriminator) and the listening-port monitor records proof of an accepting socket.
  4. On RST or bare ACK — completes the handshake discriminator: RST after SYN-ACK means half-open, ACK means a full connect.
  5. On any data-bearing packet — the shell-shape detector ingests the packet length, the beacon detector accrues client bytes, and the TLS detector judges the first client segment.
  6. Payload signatures — the five Tier 1 exploit checks.
  7. Publish — Tier 2 findings first, then Tier 1, then everything else.
Publish order is a decision, not an accident

Tier 2 findings publish before Tier 1 findings from the same packet, and Tier 2 sorts above Tier 1 in the coverage report. A payload signature tells you which of five known exploits was delivered; a behavioural finding tells you something got executed regardless of how. The generalising evidence should lead the analyst's read.

Step 4 — Post-pipeline TCP work

SYN flood counting, distributed-scan aggregation, low-and-slow scan accumulation, per-source EWMA baseline update, handshake table maintenance, and byte tracking against recently brute-forced "hot" targets.

Step 5 — UDP

UDP amplification counting, plus DNS query inspection for tunnelling.

Known asymmetry

All Tier 1 and Tier 2 inspection is TCP-only. UDP gets amplification and DNS-tunnel checks; ICMP is only counted toward the DDoS tracker. There is no exploit signature or post-exploitation behaviour rule on either. This is stated in the coverage docs rather than papered over.

4.0 — Two mechanisms that make the catalogue load-bearing

Discriminators. Each rule declares the detail keys an alert for it must carry. validate_alert_details() enforces it, and the efficacy harness fails any alert missing them — even when detection itself succeeded. This is the mechanism that stops a specific rule from silently decaying back into a generic bucket label. It is why the alert says "BRUTEFORCE_LOW_RATE at 0.031 attempts/sec on tcp/22" instead of "Brute Force Attempt".

generalizes. A boolean stating whether the rule catches a class of behaviour or only the enumerated case. Tier 1 signatures are False; Tier 2 behaviours are True. The coverage report renders the two separately so nobody reads five exploit signatures as "exploit coverage".

src_semantics. Whose IP the alert's source field represents — actor (correlate on it), target (the victim), or unknown (spoofable, never attribute). ARP spoofing is unknown because the source is forged; the correlation engine drops such events rather than grouping them under whoever the packet claimed to be.

4.1 — Reconnaissance

TCP_NULL_SCAN · TCP_FIN_SCAN · TCP_XMAS_SCAN · TCP_SYNFIN_SCANmediumsignature
Fires when
The TCP flags byte matches an exact illegal-for-a-real-connection combination. XMAS is tested as a mask (FIN|PSH|URG present, SYN/RST/ACK absent) because -sX implementations vary.
Discriminator
The decoded flag string and hex value go on the alert ("FIN,PSH,URG", 0x29), so the analyst sees which variant it was.
Why split
These four previously collapsed into one "Stealth Scan" label. An analyst could not tell a FIN scan from a NULL scan, and neither could the correlation engine or any ATT&CK mapping.
Limit
A bare SYN is deliberately not a signature — it is how every legitimate connection starts.
TCP_SYN_SCAN vs TCP_CONNECT_SCANhighbehaviouralgeneralises
Fires when
6 distinct destination ports from one source within 5 seconds.
Discriminator
The client's third packet. SYN → SYN-ACK → RST is half-open (nmap -sS). SYN → SYN-ACK → ACK means a real socket existed (nmap -sT). Port count alone cannot separate them, because both spray identical SYNs.
Auditable
Both counts ship on the alert as handshakes_completed and half_open_resets, so the classification can be checked rather than asserted.
Detail
The ports-per-second figure uses a 10 ms floor on the time span — dividing by a near-zero span once produced a nonsense "99469 ports/sec" on a live alert.
SCAN_SLOW_RATEmediumbehavioural
Fires when
12 distinct ports from one source over a 30-minute horizon, with per-port decay.
Purpose
Defeats the evasion of pacing a scan slower than the 5-second window.
SCAN_DISTRIBUTEDhighbehavioural
Fires when
4+ distinct sources each hit 3+ ports on one destination within 20 seconds.
Purpose
Catches a coordinated sweep where every individual source stays under the single-host threshold.
Attribution
Source is None — there is no single actor, so it correlates against nothing by design.
ANOMALY_TRAFFIC_BASELINEmediumbehavioural
Fires when
A source's connection count in a 10-second bucket exceeds its own learned EWMA mean by 4σ.
Maths
Exponentially weighted mean and variance, α = 0.3, minimum 6 learned buckets, and a noise floor of 20 connections so trivially small bursts are ignored.
Why
An adaptive alternative to fixed thresholds — it measures a host against itself, so a busy server and a quiet workstation get different bars.

4.2 — Credential access

BRUTEFORCE_STANDARD_RATE · BRUTEFORCE_LOW_RATEhighbehaviouralgeneralises
Fires when
8+ connection attempts to one (source, target, auth port) inside a 900-second window.
Discriminator
Measured attempts per second, computed as (n−1) intervals over the observed span. Above 0.2/s is standard rate; below is low-and-slow. The measured figure goes on the alert, so the classification is checkable.
Why one window
Both rules share a single long window and classify from the observed rate, rather than having two windows where the classification is an artifact of which one happened to trip.
Honest caveat
Shipped on every alert: this counts connection attempts. TCP completes for failed logins too, so success is not visible on the wire. Confirmation requires host_log_sensor.py.
Real regression
tcp/8080 was removed from the watched port set. It is overwhelmingly an application/API port, so ordinary polling was producing HIGH brute-force alerts. HTTP auth cannot be judged from connection counts anyway — that needs response codes this sensor does not parse.

4.4 — Tier 2: post-exploitation behaviour

Ranked above Tier 1 everywhere. These detect what a successful exploit causes, so they hold regardless of which exploit produced it — including exploits that did not exist when the code was written.

BEHAVIOR_UNEXPECTED_OUTBOUNDcriticaltier 2generalises
Fires when
A host with a known-good outbound baseline initiates a connection to a destination/port pair not in it.
Why it is clean
A server accepts connections; it does not make them. Its normal outbound count is near zero, which makes "it dialled out" an unusually unambiguous signal — no threshold tuning, no rate maths.
Two baseline sources
Configured from assets.json (trustworthy), or learned over a 300-second window. Learned findings are tagged baseline_source: "learned" so they read with that caveat — learn-on-first-sight bakes in whatever was happening at the time.
Strength
The only rule that catches a callback before a single command is typed.
BEHAVIOR_NEW_LISTENING_PORTcriticaltier 2generalises
Fires when
A host answers SYN-ACK on a port absent from its known-good snapshot.
Evidence quality
SYN-ACK is proof of an accepting socket, which a SYN alone is not.
Two-tier severity
A new port appearing within 300 s of exploit-stage traffic against that host is CRITICAL and reads as a bind shell. With no preceding exploit context it drops to MEDIUM and is described as inventory drift. The alert says which case it was.
Limit
Needs a baseline. A host with no snapshot produces nothing — silence beats a guess.
BEHAVIOR_INTERACTIVE_SHELLcriticaltier 2generalises
Fires when
A flow matches the shape of a human typing: ≥40 packets over ≥20 s, one side sending ≥60% keystroke-sized packets (≤64 bytes), ≥2× more output than input bytes, direction alternation above 0.15, and throughput under 2048 B/s.
The insight
An interactive shell has a shape no bulk protocol has — tiny packets one way, output bursts the other, turn-taking, long-lived, low-volume, human pacing. It never inspects payload content, only packet lengths, so encryption does not defeat it.
Direction-agnostic
Whichever side sends mostly-small packets is designated the "command side", so one rule covers both reverse shells (server types) and bind shells (client types).
The unavoidable FP
A legitimate SSH session is an interactive shell — same shape, same thing. No threshold separates them, so the rule does not try. It stays quiet only when vouched for: the host sensor reports a matching SSH Login for that pair, or the pair is allowlisted. With neither, it raises MEDIUM and says it could not confirm a login — a statement about evidence, not a verdict.
Real limit
Heavy packet padding blunts the small-packet signal. The 64-byte threshold catches raw shells and block-padded SSH keystrokes; a transport padding to 512 bytes will not match.
BEHAVIOR_C2_BEACONhightier 2generalises
Fires when
6+ connections to one destination inside 900 s whose inter-arrival coefficient of variation (σ/μ) is ≤ 0.25, with no interval under 2 s.
The feature
Implants check in on a timer; human and application traffic is bursty and clumped, so its interval CV is high. The CV threshold is the detector — everything else is bookkeeping. The 2-second floor stops a page load fetching 20 assets from looking metronomic.
Second feature
Per-check-in payload size CV. Timing regularity alone is shared by NTP, health checks and update agents — the dominant false-positive source. A beacon's request is a fixed structure and therefore a near-fixed size; a poller's body tracks what it is reporting.
How they combine
Both regular → promoted to CRITICAL. Timing regular but sizes varying → demoted to MEDIUM and described as a scheduled poller. No size data → catalogue severity with size_evidence: "unavailable", never implying a measurement that was not taken. Interval CV remains the gate.
Detail
Only client bytes count — reply sizes vary legitimately even for a real implant. The in-flight check-in is excluded from the maths, since it has sent nothing yet.
BEHAVIOR_CLEARTEXT_ON_TLS_PORTcriticaltier 2generalises
Fires when
The first client data packet on a TLS-convention port (443, 465, 563, 636, 989, 990, 993, 995, 5061, 6697, 8443) does not open with a TLS handshake record.
The test
Three bytes at a fixed offset: 16 03 0x — content type 22, major version 3. Every TLS version from 1.0 to 1.3 opens this way, because 1.3 keeps a legacy record version on the wire for middlebox compatibility. Legacy SSLv2 ClientHello is also accepted so it is never called cleartext.
Why it matters
Attackers pick 443 because egress filters allow it, and commodity tooling frequently does not bother wrapping the channel in real TLS. No baseline, no threshold, verdict on one packet — where the shape rule needs ~40 packets over ~20 s of typing.
Guard 1
Only flows whose SYN was observed are judged. Mid-stream, a TLS application-data record (type 23) is indistinguishable from cleartext to a first-byte test, so a sensor starting mid-session renders no verdict rather than a guess.
Guard 2
The SYN's sequence number is recorded, so a reordered or retransmitted later segment is skipped instead of judged as the opening bytes.
Classification
Cleartext HTTP → MEDIUM (a listener on the wrong port is a real misconfiguration). Anything else → CRITICAL. The first bytes ship in hex so an analyst can check the call.
Limit
A C2 that uses genuine TLS is invisible here, and mature frameworks do. JA3/JA4 fingerprinting is what addresses that, and it is not implemented.
Not watched
STARTTLS ports (587, 143, 21, 25) are deliberately excluded — opening in cleartext is correct behaviour there.
BEHAVIOR_UNCOMMON_EGRESS_PORThightier 2generalises
Fires when
An internal host opens an outbound session to the internet on a port outside the common-client set.
Position
Explicitly the weaker fallback — a global port heuristic rather than a per-host baseline. It exists to cover hosts absent from the asset inventory, and it defers to BEHAVIOR_UNEXPECTED_OUTBOUND for any host that has one.
The hole it leaves
It exempts exactly the ports an attacker would choose (443, 80, 53, 22…). That hole is why the shape rule and the TLS rule exist.

BREACH_SESSION's reasoning is worth being able to state: TCP completes for failed logins too, so connection establishment proves nothing. Byte volume of the session afterwards is the honest packet-level discriminator between a failed attempt and a successful one. The alert carries confidence: "medium (network-inferred; confirm via host auth logs)" rather than claiming certainty.

EXFIL_DNS_TUNNEL's heuristic is a query qualifying if any of: the record type is TXT/NULL/IXFR/AXFR; a single label exceeds 45 characters; or the name exceeds 60 characters and the subdomain's Shannon entropy is ≥ 3.6 bits/char, which is what base32- or hex-encoded payload looks like.

MITM_ARP_SPOOF has two modes. With an asset inventory it knows the correct MAC, so it names the impostor and marks the finding verified: true. Without one it learns on first sight and reports a MAC change as unverified — because the sensor may have started mid-attack, in which case first-seen-wins would blame the victim.

05Fragment reassembly

This is a good story to be able to tell, because it is a complete evasion that worked, a precise explanation of why, and a fix that normalises rather than blocks.

nmap -f splits the 20-byte TCP header across 8-byte IP fragments. Only the first fragment carries the source and destination ports, at offsets 0–3. The flags byte lives at TCP offset 13 — which lands in the second fragment. So a rule engine inspecting fragments as they arrive sees:

  • fragment 0 — ports, but no flags
  • fragment 1 — flags, but no ports and no parseable TCP layer at all

Neither matches a scan signature. The scan was completely invisible. Reassembling before rule matching means a fragmented -sF normalises to exactly the same TCP_FIN_SCAN as an unfragmented one, and every downstream rule sees an ordinary packet.

Design decisions inside it

  • Datagram key is (src, dst, ip_id, proto) — the correct key per RFC 791. ip_id alone collides across hosts.
  • Coverage is tracked as merged byte intervals, not a fragment count. The classic evasion is sending overlapping and conflicting fragments; a count can be faked, an interval set cannot.
  • First-writer-wins on overlaps, mirroring BSD/Linux policy, with the overlap recorded in stats. Overlapping-fragment evasion works because stacks resolve conflicts differently — dropping the datagram entirely would hand the attacker an easy bypass, so we pick a policy and match against the result.
  • Bounded on every axis: 30-second timeout, 1024 concurrent buffers, 128 fragments per datagram, 65535-byte cap. Anything dropped is counted and surfaced via /status rather than disappearing.
  • Pure-bytes core plus a thin scapy adapter, so the reassembly logic is unit-tested without a packet library.

Alerts produced from a reassembled datagram are annotated evasion_attempted: "IP fragmentation (nmap -f)", so the attempt stays visible rather than being silently normalised away.

06Correlation engine

The previous engine's output looked arbitrary. Diagnosing exactly why, then writing a specification before writing the replacement, is the most transferable piece of work in the project.

What the old one did

It appended alert type strings to a per-source list, then tested four hardcoded set.issubset rules plus a catch-all of "3 or more distinct types". Three defects followed:

  • No time window anywhere. Nothing carried a timestamp; nothing was ever pruned by age. Events from hours apart combined freely.
  • Source was not consistently the actor. Data staging filed under the collecting host (the victim); ARP spoofing filed under the forged IP (never the attacker); distributed scan passed None. So one bucket mixed attacker-attributed and victim-attributed events.
  • The catch-all was trivially satisfied. A single nmap -sS run produces more than three distinct alert types, so one scan manufactured a CRITICAL "Multi-Vector Attack".

The specification the replacement implements

Grouping key: source IP, and only source IP. Destination was considered and rejected — it would split one attacker sweeping three hosts into three incidents, the opposite of what an incident is for. Destinations are recorded as evidence on the incident instead.

Actor attribution is a refinement, not a second key. Detectors pass an explicit actor, and events whose source semantics are unknown (forged) are dropped rather than grouped under whoever the packet claimed to be.

Promotion rule. An incident opens only when a source's buffered events show forward progression through the kill chain — there exist events e₁, e₂ with ts(e₁) ≤ ts(e₂) and stage_index(e₁) < stage_index(e₂).

0Reconnaissance1Credential Access2Initial Access3Privilege Escalation4Persistence5Command & Control6Lateral Movement7Collection8Exfiltration

Every consequence of that rule is deliberate:

  • Five port scans do not open an incident. Neither does a port scan plus a slow scan plus a flag signature — all reconnaissance, no advancement.
  • Recon followed by an exploit attempt does.
  • The reverse order — C2 at t=0, recon at t=30 — does not. Nothing advanced.
  • Stage-less events (floods, ARP) never open an incident but do attach to an open one as context.
  • INFO-severity events never open one and never attach.

Severity is the worst member alert, escalating to CRITICAL at three or more distinct stages. The escalation is gated on stage count, not alert count — a single nmap run satisfies "three distinct alert types" but cannot satisfy three distinct kill-chain stages.

Determinism under concurrency

Ingest, evaluate and mutate happen inside one critical section, removing the old check-then-act race. Progression is computed over the buffer sorted by event timestamp, not arrival order — so N threads delivering the same N events in any interleaving produce byte-identical grouping. A test asserts this with 8 threads over a shuffled sequence.

Bounded: 600-second default window, 4096 tracked sources under LRU eviction (open incidents are never evicted), 500 stored events per incident with the overflow still counted. A --rand-source flood cannot exhaust memory.

Separately, main.py maintains a simpler per-host intrusion state that classifies each host as QUIET / PROBING / UNDER ATTACK / BREACHED / ACTIVE INTRUSION. That is what powers the dashboard's Intrusion Status panel and answers the operator's actual question: is this host just poking at us, or is it inside and moving?

07Alert retention and deduplication

The old store was deque(maxlen=500) — a fixed ring where 200 identical port-scan pings from one host silently pushed every CRITICAL off the end. Two independent defects with one symptom: no severity weighting, and no deduplication.

Retention by severity

SeverityTTLEviction order under capacity pressure
criticalindefinitelast
highindefinitefourth
medium24 hthird
low6 hsecond
info1 hfirst

Capacity is 5000 records. Eviction sorts by (severity rank, age), so a CRITICAL is only dropped once every INFO, LOW, MEDIUM and HIGH is already gone — at which point something is very wrong and the audit log says so.

Deduplication

Alerts identical on (rule_id, src, dst, dst_port, severity) within a rolling 300-second window collapse into one record carrying count, first_seen and last_seen. 200 identical pings become one record with count: 200.

Destination port is in the key on purpose. A scan sweeping 200 ports is one scan, but the per-port alerts are genuinely different facts. It is the repeated alert for the same port that is redundant.

A subtle consequence handled explicitly: alert IDs are assigned only after an alert survives deduplication. Otherwise every collapsed repeat would burn an ID and leave gaps in the sequence that look like lost alerts.

Nothing vanishes silently

Every eviction and every collapse is written to an audit log exposed at GET /alerts/retention. If an alert is gone, the log says which rule it was, how many were folded into it, and why it went. The dashboard reports both "records" and "alerts represented", because showing only the record count would under-report the attack.

08Baselines: assets.json

Tier 2's strongest rules diff against a known-good baseline. The file supplies four things:

  • hosts — per-host listening_ports (feeds the bind-shell rule), plus either an explicit allowed_outbound list or learn_outbound: true.
  • trusted_arp / gateway — the trust anchor that turns "a MAC changed" into "this MAC is the impostor".
  • authorized_scanners — IPs whose reconnaissance is recorded at INFO instead of suppressed. An unlisted host running the same scan still alerts at full severity; this is an allowlist, not a weakened rule.
  • authorized_shell_sessions — [client, server] pairs exempt from the interactive-shell rule, for hosts where the host sensor is not deployed.

The file is optional, and the startup path is explicit about what is switched off without it: ARP falls back to learn-on-first-sight, rogue-host detection is off, and Tier 2 has nothing to diff against. That warning exists because a sensor could otherwise run with its strongest post-compromise rules silently doing nothing.

baseline_assets.py generates a starter block from a pcap or live capture. Two caveats ship with it and both are worth repeating in an interview:

The baseline trap

A baseline taken from a compromised host bakes the compromise in. If the C2 channel is active during the capture, the tool faithfully records it as normal and the sensor will never alert on it again.

Port collapsing re-blinds the rule. By default a port seen reaching 5+ destinations is widened to "any destination", which keeps browser traffic manageable — but a reverse shell on that port no longer trips the outbound rule. --collapse-after 0 keeps every destination explicit. The generated file flags which ports were widened and what that cost.

The design response to both: the output is annotated with what was seen and how often, so an entry that looks wrong is visible rather than buried in a list of ports. It is a starting point for review, not an answer.

Reads Linux auth.log-format files and detects what neither packet capture nor flow logs can see, because it happens above the network layer:

This sensor closes the honesty gap in the network rules. Network detection can only infer a breach from traffic volume; auth logs confirm one. And privilege escalation and persistence are network-invisible entirely — the auth log is the only truthful source for them.

It also feeds back: an SSH Login alert calls note_authorized_session(), which is the sole mechanism that keeps a legitimate SSH session from tripping BEHAVIOR_INTERACTIVE_SHELL.

cloud_log_sensor.py — log-native detection

Reads AWS VPC Flow Log files with no network privileges, no traffic mirroring, and no cloud account. Detects impossible travel (one source IP in two distant regions rapidly), log-based port scanning, exfiltration by byte volume, API abuse, brute force from REJECT flows, UDP amplification, and lateral movement.

The interesting inversion: cloud metadata (IMDS) access lives in the packet sensor, not this one, because 169.254.169.254 is link-local and VPC Flow Logs do not record it. Two telemetry sources with genuinely complementary blind spots is the point.

live_ids_v2.py — the ML sensor

Captures packets, assembles per-flow feature vectors, runs inference on mature flows (≥5 packets), and POSTs alerts. Flows expire after 120 s to bound memory. It runs standalone against a pcap for offline evaluation, or live against an interface. See §10.

Two models trained on CIC-IDS2017, both multiclass HistGradientBoosting, both reported with metrics that are not flattering — which is the point.

Train/serve alignment

The feature list is defined once in feature_engineering/live_features.py, and both the trainer and the sensor import it. Order is fixed: numeric features first, then the one-hot encoding appended.

The reason this matters is a specific mistake the project made and then corrected. The original NSL-KDD pipeline trained on all 41 features while the live sensor could only compute about 13, zeroing the rest. That is a train/serve distribution mismatch — the model leans on columns that are always zero in production. The fix was to define the live-computable subset as the single source of truth and train only on it.

Two approximations are documented rather than hidden: NSL-KDD's count/srv_count are defined over a 2-second window of connections to the same host/service, which the live sensor approximates with per-flow packet intensity (correlated, not identical); and CIC-IDS's flag counts are whole-flow aggregates, so the derived flag/serror_rate/rerror_rate are approximations of the sensor's per-packet state machine.

Evaluation honesty

CIC-IDS2017 ships no canonical train/test split, so this uses a stratified 75/25 hold-out with a fixed seed. That is in-distribution — same capture week, same network — so these figures are an optimistic upper bound relative to a fresh deployment, not a generalisation estimate.

Where ML sits in the architecture: it is one alert source among four, arriving as ML_FLOW_ANOMALY at MEDIUM severity. It is not the detection engine. The rule layer carries the load, and the reason is stated plainly — a rule can explain itself with the measurement that triggered it, and a gradient-boosted tree cannot.

11API, authentication and authorisation

Two separate authentication systems

Humans get bearer tokens: 32 random bytes hex-encoded, stored in SQLite with an 8-hour expiry, purged on every validation. Sensors get a pre-shared key on an X-Sensor-Key header, compared with hmac.compare_digest. The sensor path deliberately does not accept user tokens and the user path does not accept the sensor key — so a leaked sensor key permits alert injection, never alert disclosure.

Passwords

PBKDF2-HMAC-SHA256, 200,000 iterations, 16-byte random salt, stored as pbkdf2$sha256$<iters>$<salt>$<hash>, verified in constant time. Legacy unsalted SHA-256 hashes are still verifiable and are transparently upgraded to PBKDF2 on next successful login — migration without locking anyone out.

A real finding in this project's own history

The repo shipped a documented default admin password (nids@admin123) until 2026-08-11. A default password in a public repository is not a default — it is a published credential. Worse, the project's own user database was committed before *.db was gitignored, and that blob is still reachable in git history. Impact was assessed as low only because the hash was of the password the README already stated in plain text.

The lesson, which is the part worth saying out loud: .gitignore prevents future commits; it does not remove what is already published. Adding the ignore rule felt like a fix and was not one. The actual fix was to generate a random 20-character password per deployment and print it once at startup, so nothing publicly known can log in.

Three silent failures that were fixed together

These are worth knowing because "the NIDS looked dead" was a real incident, and the causes were all about honest state reporting:

  • The capture interface was hardcoded to ens37, which exists only on the lab sensor VM. Anywhere else it captured nothing and reported success. Now NIDS_IFACE, with auto supported and available interfaces listed on error.
  • The capture thread died on exception while running stayed True — the dashboard showed a live sensor capturing zero packets forever. Now the error is recorded in system_stats["sniffer_error"], surfaced through /status, and running is set false in a finally.
  • The dashboard hardcoded its API origin, so browsing from another machine silently talked to the wrong host. It now derives the API base from whichever origin served the page.

A fourth, related: the capture loop runs in one-second timeout slices rather than one blocking sniff(), because stop_filter is only evaluated when a packet arrives — on a quiet link, a stop request would otherwise hang until the next packet.

Two layers

Unit tests (163 across 9 modules) exercise each detector in isolation with an injected fake clock — no sleeping, no network, whole suite in under 0.1 s.

The efficacy harness is the more unusual artifact. It runs 36 scored scenarios through the real pipeline and reports true positives, false positives and false negatives per attack category. It exists because every finding from a manual TP/FP/FN testing round has a case here, so a regression shows up as a failing case rather than a surprise during the next manual round. It exits non-zero, so it can gate a commit.

The mechanism that keeps specificity from rotting

Beyond firing or not, the harness checks every alert against its rule's declared discriminators. A rule that detects the attack but emits a featureless detail dict FAILS the case. That is what prevents a specific rule from quietly decaying back into a generic bucket label — the exact regression the rule-ID work was meant to prevent.

The benign half is the important half

Twelve of the 36 scenarios assert zero alerts above INFO and zero incidents: a subnet service check, allowlisted nmap, failed-login noise, bursty curl, a normal SSH session, normal FTP login, normal IRC chat, real HTTPS, STARTTLS SMTP on 587, host-sensor-confirmed SSH, allowlisted-pair SSH, and a bulk file transfer. Several are precise negative cases for a specific rule — normal FTP for the vsftpd signature, normal IRC for UnrealIRCd, bulk transfer for the interactive-shell shape.

Two regressions found by the tests themselves

  • tcp/8080 in the brute-force watch list, turning ordinary API polling into HIGH brute-force alerts. Caught by a benign regression test.
  • Non-ASCII characters in alert text. An arrow in an alert message raised UnicodeEncodeError on a cp1252 stdout — inside the capture thread, killing the alert and returning 500 on the API path. This was the same bug fixed once before and reintroduced, because the original fix was "keep the strings ASCII" — a promise every future call site has to remember. It is now handled once, at the single point alerts are written out, so it cannot recur.

That second one generalises into a principle worth stating: a fix that depends on everyone remembering a rule is not a fix. Put the guarantee at the chokepoint.

Run it with the right interpreter

The harness's fragmented-scan case needs scapy and silently returns early without it, scoring as a false negative. Run venv\Scripts\python.exe efficacy_harness.py — the system Python will report a phantom 35/36.

13Coverage and limits

This section is the one most worth rehearsing. Any interviewer who knows the field will test whether the limits of the telemetry are understood, and "I know exactly what my sensor can and cannot prove" is the senior answer.

The scope statement, stated first everywhere

This is network-only detection. It sees packets on the monitored segment and infers everything from them. It has no host, process, or EDR visibility. It therefore cannot see:

  • code executing in memory, or any action producing no packets
  • an exploit delivered inside a TLS session it cannot decrypt
  • local privilege escalation
  • anything on a host whose traffic never crosses the monitored segment
  • whether a login actually succeeded — TCP completes for failed logins too

Untested rule logic

Coverage should never be described as complete without saying so.

14Known gaps and what comes next

The single highest-leverage missing component is a per-host behavioural profile store. Look at what nearly every remaining detection idea has in common — "first time", "unlike this host normally", "relative to its own history". Once a store of peers, ports, volume, direction ratio, active hours and TLS fingerprints exists, half the remaining rules become one-liners against it.

What exists today is one narrow slice: the outbound anomaly detector keeps {host: {(dst, port)}}, but only for monitored hosts and only for outbound SYNs. Nothing anywhere records typical volume, direction, or timing per host.

Falls out of the profile store

  • First-time peer on an admin port — catches the single deliberate hop that a fan-out threshold of 6 structurally cannot see.
  • Ratio flip — a host that normally downloads starts uploading. The current 50 MB / 300 s absolute threshold misses this entirely and fires on legitimate backups.
  • Slow-drip exfiltration — needs cumulative per-host, per-destination, per-day accounting, which a 300-second sliding window cannot express at any threshold.
  • JA3/JA4 as per-host novelty — "a TLS fingerprint never seen before from this host" is computable and defensible; "a fingerprint matching no known browser" needs a curated corpus that is not available here.

It also fixes alert fatigue: baseline deviation gives a natural ranking signal, so alerts get ordered instead of suppressed. The disciplined way to do that is a separate confidence field the dashboard sorts by — feeding a continuous score into catalogue severity would make severity non-reproducible across restarts.

Deferred with a stated reason

All the Active Directory detections — Kerberoasting (many TGS requests for distinct SPNs), DCSync (DRSUAPI replication from a non-DC), AS-REP roasting, RC4 downgrade, workstation-to-workstation SMB, bulk LDAP — are high fidelity and fully network-visible. They are deferred because the lab is Kali / Metasploitable / Ubuntu with no domain controller, so they cannot be fired even once. Shipping rules that can never be tested would undercut the project's main strength.

Also open

  • UDP and ICMP carry no Tier 1 or Tier 2 inspection.
  • The CIC-IDS multiclass model is trained but the live sensor still serves a binary verdict; wiring the multiclass prediction through to the dashboard is unfinished.
  • The interactive-shell and TLS detectors have sweep() methods that no periodic task calls. Both are bounded by flow caps and close-on-FIN, so nothing leaks — but the sweep is dead code until a maintenance tick exists.

15Questions to be ready for

The ones an experienced interviewer actually asks, and the answer that holds up.

Why build this instead of deploying Suricata or Zeek?

For production I would deploy Zeek. The point of building it was to understand detection engineering from telemetry up: what feature separates two things that look alike on the wire, how confident that feature lets you be, and where it stops working. You cannot learn that from writing config. The portable version of the work is the reasoning — and I would move the log-shaped host-sensor rules into Sigma to close the toolchain gap, while keeping the stateful flow analytics (interval CV, turn-taking ratios) in code, because Sigma cannot express them.

How do you know any of it actually works?

Two layers. 163 unit tests drive each detector with an injected clock. Then a 36-case efficacy harness runs real attack and benign scenarios through the same pipeline the live sensor uses and reports TP/FP/FN — currently 25 true positives, zero false positives, zero false negatives. Eleven of the 36 are benign scenarios that must produce nothing above INFO. And the harness fails any alert that fires without its rule's declared discriminating features, so a rule cannot pass by detecting the attack while emitting a useless message.

What is your false-positive story?

Three mechanisms. First, benign regression scenarios in the harness that must stay silent. Second, discriminators that make each rule specific rather than broad — brute force splits on measured rate, port scan on the handshake outcome. Third, and most important, rules that state their uncertainty instead of hiding it: the interactive-shell rule cannot distinguish a shell from legitimate SSH, so rather than tuning a threshold that does not exist, it drops to MEDIUM and says it could not confirm a login. That is a statement about evidence, not a verdict.

The known FP sources are named too: beaconing versus scheduled pollers, which the payload-size CV addresses; and any learned baseline, which is tagged as learned on every finding it produces.

Nearly all C2 is TLS now. How do you detect anything?

By not looking at payload. Four things survive encryption: direction, timing, volume, and fingerprint. Beaconing is detected from the coefficient of variation of inter-arrival gaps and the consistency of per-check-in byte counts — both measured without reading a single payload byte. An interactive shell is detected from packet lengths and turn-taking, not content. Direction inversion — a server initiating outbound — needs no payload at all.

And there is one cheap thing worth doing before any of that: check whether traffic on 443 actually is TLS. Three bytes at a fixed offset. Attackers pick 443 for the egress filter, and commodity tooling often does not bother wrapping the channel. What I do not cover is a careful operator using real TLS — that needs JA3/JA4, and I would say so rather than imply otherwise.

Your model's accuracy is 96% — is that good?

No, and accuracy is the wrong number to quote. BENIGN is about 80% of CIC-IDS2017, so predicting BENIGN always scores well. The honest figure is macro F1, which is 0.656 for the model the sensor actually serves. That means it is mediocre at distinguishing attack types. The full-flow reference model reaches 0.861, and the gap is exactly what it costs to collapse 78 flow statistics into 13 packet-derivable features.

I would also flag two things unprompted: the hold-out is in-distribution, same capture week, so it is an optimistic upper bound and not a generalisation estimate. And destination port is the top feature in both models, which is a real weakness of CIC-IDS — the model can score well by learning the lab's port assignments rather than attack behaviour.

What can this system not detect?

Execution, defense evasion and local privilege escalation — none of them produce packets, so a network sensor cannot see them regardless of rules. Persistence only in the narrow slice that opens a listening port. Anything inside a TLS session I cannot decrypt. Whether a login succeeded, because TCP completes for failed logins too. And anything on a host whose traffic never crosses the monitored segment.

That is why the host auth-log sensor exists — it is the only source that knows rather than infers, and it covers exactly the tactics the network sensor structurally cannot.

Why correlate on source IP only? Isn't that naive?

It is deliberate and I considered the alternatives. Adding destination as a key would split one attacker sweeping three hosts into three incidents, which is the opposite of what an incident is for — so destinations are recorded as evidence on the incident instead. The real subtlety is not the key, it is attribution: some detectors file under the victim rather than the attacker, and ARP spoofing's source IP is forged. So each rule declares its source semantics, and events that are unattributable get dropped rather than grouped under whoever the packet claimed to be.

The grouping key was never the reason the old engine looked random. The reason was that it had no time window at all and a catch-all rule of "three distinct alert types", which a single nmap run satisfies.

What happens under a flood — does it fall over?

Every stateful structure is explicitly bounded. Correlation tracks 4096 sources under LRU eviction and 500 events per incident with the overflow still counted. The reassembler caps at 1024 concurrent buffers, 128 fragments per datagram, 65535 bytes, 30-second timeout. Flow tables in the shell and TLS detectors cap at 8192 and evict oldest-first. The alert store holds 5000 records and evicts lowest-severity-oldest-first, so a critical survives until everything else is gone.

The design rule throughout: anything dropped is counted and reported — through /status or the retention audit log — rather than disappearing silently. A --rand-source flood degrades the sensor's memory of low-value events; it does not exhaust memory and it does not hide the critical alerts.

How do you handle evasion?

Concretely, for fragmentation: nmap -f evaded everything, because the flags byte and the ports land in different fragments and neither piece matches a signature. The fix reassembles before rule matching, so a fragmented scan normalises to the identical rule as an unfragmented one — and the alert is annotated that fragmentation was attempted, so the evasion stays visible.

Overlapping-fragment evasion is handled by tracking coverage as merged byte intervals rather than a fragment count, and by picking an explicit resolution policy (first-writer-wins, matching Linux) instead of dropping conflicted datagrams, which would itself be a bypass.

Rate-based evasion is covered by pairing every short window with a long one: a 5-second port-scan window plus a 30-minute low-and-slow rule; a fast brute-force rule plus a low-rate one over 900 seconds.

Talk me through a bug you found and what you changed because of it.

An alert message containing a Unicode arrow raised UnicodeEncodeError on a Windows cp1252 console — inside the packet capture thread. It killed the alert entirely, and returned a 500 on the API path. I had fixed the same class of bug once before, and it came back.

What made it recur is the interesting part: the first fix was "keep alert strings ASCII", which is a promise every future call site has to remember. The second fix put the encoding guarantee at the one place alerts are written out. That changed how I think about fixes generally — if a fix depends on everyone remembering a rule, it is not a fix, it is a note. Put the guarantee at the chokepoint.

What would you build next, and why that?

A per-host behavioural profile store — peers, ports, volume, direction ratio, active hours, TLS fingerprints. Nearly every remaining detection idea I have is phrased as "first time" or "unlike this host normally", and none of them are expressible without it. First-time peer on an admin port catches the single deliberate lateral hop that my fan-out threshold of six structurally cannot. A ratio flip catches the host that quietly turns from downloader to uploader, which my absolute 50 MB threshold both misses and false-positives on. Slow-drip exfiltration needs cumulative per-day accounting that a 300-second window cannot express at any threshold.

It also solves alert fatigue as a side effect: deviation from a host's own baseline is a natural ranking signal, so I could order alerts instead of suppressing them. One component, two problems.

What's the weakest part of this project?

Ten rules have IDs and discriminators but their detection logic predates the rebuild and the harness does not exercise it — distributed scan, slow scan, ARP, DNS tunnel, exfil, staging, IMDS, lateral, breach. I know they are the untested set and I would not describe coverage as complete without saying so.

Second: main.py is still 2257 lines and holds detectors that ought to live in the package. The migration is real but incomplete, and the tell is that those are precisely the untested ten.

Third: the ML side is honest but under-integrated — a multiclass model is trained and evaluated, and the live sensor still serves a binary verdict.
